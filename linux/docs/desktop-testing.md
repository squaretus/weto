# Проверка на живом рабочем столе

Как проверить Linux-версию с Mac — и глазами, и функционально, в одном сеансе.

Машины поднимаются через OrbStack: в его ядре есть WireGuard и `/dev/net/tun`,
поэтому настоящий туннель там создаётся, а не имитируется. Рабочий стол — KDE:
у него StatusNotifierItem родной, без плагинов и расширений, и это одна из двух
целевых сред.

## Подготовка

```bash
linux/scripts/desktop-machine.sh ubuntu       weto-ubuntu   # последняя Ubuntu
linux/scripts/desktop-machine.sh arch         weto-arch
```

Без версии OrbStack ставит последнюю Ubuntu — на ней и проверяем. Отдельно стоит
хотя бы раз пройтись по LTS:

```bash
linux/scripts/desktop-machine.sh ubuntu:noble weto-noble    # пол GTK 4.14
```

24.04 несёт GTK 4.14 — заявленный пол проекта. Только там видно правила, которые
на свежем GTK работают, а на LTS молча отбрасываются: из-за этого в проекте нет
CSS-переменных, и следующая такая находка обнаружится тем же способом.

Скрипт создаёт машину, ставит KDE и зависимости, собирает weto из рабочего дерева
(отдельным каталогом сборки, чтобы не мешать артефактам с Mac), устанавливает его,
поднимает VNC и ssh-туннель. Дальше с Mac:

```bash
open vnc://127.0.0.1:5901        # пароль VNC: weto
```

Туннель обязателен: порты машин OrbStack с Mac напрямую недоступны — не отвечает
ни имя `.orb.local`, ни адрес, ни ICMP, при полностью пустых правилах фильтрации
внутри машины. Через ssh всё работает.

Пароль VNC нужен клиенту macOS: с сервером без авторизации «Общий экран» не
соединяется вовсе, хотя сервер при этом исправен — рукопожатие доходит до кадрового
буфера. Это сущность отдельная от пароля пользователя Linux: у того пароля нет вовсе
(`passwd -S` отвечает `NP`), и sudo в машине работает без него.

Утилиты `vncpasswd` в Ubuntu 24.04 нет ни под одним именем, поэтому файл паролей
скрипт собирает сам — формат открытый, восемь байт под DES с общеизвестным ключом.
`-provider legacy` там обязателен: в OpenSSL 3 DES уехал в legacy-провайдер, и без
него команда молча отдаёт текст ошибки вместо шифротекста.

Если туннель отвалился (например, машину перезапустили):

```bash
ssh -f -N -L 5901:127.0.0.1:5901 weto-ubuntu@orb
```

Если вместо рабочего стола висит заставка — это экран блокировки KDE. Он всплывает
на старте сеанса даже при выключенном автоблокировании, а пароля у пользователя нет,
так что сквозь него не пройти. Скрипт снимает блокировщик сам; снятый один раз он
не возвращается. Вручную:

```bash
orb -m weto-ubuntu bash -lc 'pkill -x kscreenlocker_g'
```

Убивать процессы в машине надо по имени (`pkill -x`), а не по командной строке:
`pkill -f` находит и сам шелл, в котором набрана команда, — искомые слова есть
в нём самом, и сеанс убивает себя вместо цели.

Машины намеренно `amd64`: релиз выпускается под x86_64, и проверять надо его.
Переопределяется переменной `WETO_MACHINE_ARCH=arm64`, если нужна скорость.

## Часть первая: глазами

В сеансе KDE запустить `weto` из меню приложений или из терминала **внутри сеанса**.

Запуск через `orb -m weto-ubuntu` для этой части не годится: у такого шелла своя шина
D-Bus, а `StatusNotifierWatcher` живёт на шине сеанса Plasma. Приложение тогда честно
скажет «трея в этом окружении нет» и уйдёт в окно — это правильный путь для ванильного
GNOME, но проверять на нём трей бессмысленно. Если запускать всё-таки снаружи, шину
надо взять у сеанса:

```bash
orb -m weto-ubuntu bash -lc '
  bus=$(tr "\0" "\n" < /proc/$(pgrep -x plasmashell | head -1)/environ \
        | grep ^DBUS_SESSION_BUS_ADDRESS= | cut -d= -f2-)
  DISPLAY=:1 DBUS_SESSION_BUS_ADDRESS="$bus" nohup weto >/tmp/weto.log 2>&1 &'
```

- [ ] Иконка появилась в трее.
- [ ] Наведение показывает заголовок статуса.
- [ ] Левый клик открывает окно статуса; правый — меню из трёх пунктов.
- [ ] Щит и заголовок совпадают по цвету; рядом с цветом всегда есть текст.
- [ ] Карточки, отступы и капсы совпадают с `docs/design-system.md`.
- [ ] Переключение темы в настройках перекрашивает оба окна сразу.
- [ ] Вкладка «Журнал» показывает записи, диагностическая строка выделяется мышью.

Ванильный GNOME проверяется отдельно и ради одного: **трея там нет**, и приложение
обязано остаться доступным. Ставится `gnome-session` вместо KDE; проверять надо
ярлык в меню приложений и повторный запуск `weto`, который поднимает окно уже
работающей копии, а не второй процесс.

## Часть вторая: функционально

### Туннель и завершение целей

Настроить цель и интерфейс:

```bash
orb -m weto-ubuntu bash
mkdir -p ~/.config/weto && chmod 700 ~/.config/weto
printf '%s' "<токен ipinfo>" > ~/.config/weto/token && chmod 600 ~/.config/weto/token
```

В настройках приложения добавить целью `/usr/bin/nano` и выбрать туннель.
Туннеля пока нет — список пуст, и на это есть подсказка. Создаём:

```bash
orb -m weto-ubuntu -u root bash -c '
  ip link add dev wg0 type wireguard
  ip addr add 10.9.0.2/24 dev wg0
  ip link set wg0 up
'
```

- [ ] `wg0` появился в списке туннелей **без перезапуска приложения**.
- [ ] Выбор `wg0` меняет статус: маршрут через него не идёт, значит «VPN поднят,
      но трафик идёт мимо него», цели завершаются.

Отдаём туннелю маршрут — так же, как это делает `wg-quick`, через свою таблицу:

```bash
orb -m weto-ubuntu -u root bash -c '
  ip route add default dev wg0 table 51820
  ip rule add not fwmark 51820 table 51820 priority 32764
'
```

- [ ] Статус стал «На страже» (гео-проба уйдёт в никуда через мёртвый туннель —
      для проверки самой логики маршрута достаточно, что охрана видит владельца).
- [ ] Запущенный `nano` виден пилюлей в окне статуса.

Роняем туннель:

```bash
orb -m weto-ubuntu -u root ip link set wg0 down
```

- [ ] `nano` завершился меньше чем за секунду.
- [ ] Пришло уведомление о завершении.
- [ ] В журнале появилась запись с причиной «VPN не поднят».

### Скриптовая цель

```bash
orb -m weto-ubuntu bash -c 'readlink -f "$(command -v npx)"'
```

Вписать полученный путь целью, запустить `npx`, уронить туннель.

- [ ] `npx` завершился, хотя `/proc/<pid>/exe` указывает на `node`.
- [ ] Другие процессы `node` живы.

### Обновление

Проверяется настоящим релизом — так же, как на macOS, и по тем же причинам:
приложение ходит только в GitHub, и подменять ему источник нечем.

Порядок тот же, что в `runbooks/release.md`:

1. Выпустить черновой тег на версию выше установленной, дождаться, пока
   релизный workflow соберёт обе платформы.
2. Убедиться, что в релизе есть архив под Linux — `weto-<версия>-x86_64-linux.tar.zst`.
   Релиз без него приложение не считает находкой и молчит, и это правильно:
   окно, которое ничего не установит, хуже молчания.

```bash
curl -s https://api.github.com/repos/squaretus/weto/releases/latest \
  | grep -E '"tag_name"|x86_64-linux'
```

Дальше в машине:

- [ ] В течение часа (или сразу после перезапуска) в окне статуса появился
      баннер «Доступно обновление».
- [ ] Кнопка открывает окно с версией и заметками релиза.
- [ ] «Позже» прячет баннер; после перезапуска он не возвращается — отсрочка
      хранится абсолютной датой и переживает перезапуск.
- [ ] «Пропустить эту версию» прячет её насовсем, а «Проверить обновления»
      в настройках возвращает: это единственный и достаточный способ снять пропуск.
- [ ] «Обновить» показывает шкалу, приложение перезапускается само,
      и `weto --version` сообщает новую версию.
- [ ] Прежняя версия осталась на диске: `ls ~/.local/share/weto/`.

### Откат

Подложить в новую версию заведомо нерабочий бинарник и запустить дважды:

```bash
orb -m weto-ubuntu bash -c '
  printf "#!/bin/sh\nexit 1\n" > ~/.local/share/weto/9.9.9/bin/weto
  chmod +x ~/.local/share/weto/9.9.9/bin/weto
  weto; weto; readlink ~/.local/share/weto/current
'
```

- [ ] `current` вернулся на предыдущую версию.

### Установка и удаление

```bash
orb -m weto-ubuntu bash -c '~/.local/share/weto/current/share/uninstall.sh; find ~ -name "*weto*" | head'
```

- [ ] После удаления не осталось ни одного файла weto.

## Приложения на Electron в этом сеансе

ChatGPT, Slack, VS Code и прочий Electron требуют доступа к GPU и отказываются
рисовать окно без него: в логе будет «GPU access not allowed». В сеансе VNC
видеоускорения нет, процесс GPU падает, и Electron запоминает блокировку —
после этого он не запустится даже когда причина устранена.

Лечится программным растеризатором, а не флагом `--disable-gpu`: тот запрещает
GPU совсем, и приложение отказывается тем же сообщением.

```bash
orb -m weto-ubuntu bash -lc '
  rm -rf ~/.config/<Имя>/GPUCache ~/.config/<Имя>/"Local State"   # сбросить память о падениях
  bus=$(tr "\0" "\n" < /proc/$(pgrep -x plasmashell | head -1)/environ \
        | grep ^DBUS_SESSION_BUS_ADDRESS= | cut -d= -f2-)
  DISPLAY=:1 DBUS_SESSION_BUS_ADDRESS="$bus" LIBGL_ALWAYS_SOFTWARE=1 \
    nohup chatgpt --use-gl=angle --use-angle=swiftshader \
                  --ignore-gpu-blocklist --disable-gpu-sandbox >/tmp/chatgpt.log 2>&1 &'
```

К охране это отношения не имеет: цель завершается по сигналу независимо от того,
чем она рисует окно. Но без окна её неудобно запускать руками.

## Чего эти машины не покажут

**Wayland.** Сеанс идёт через VNC, то есть по X11. Единственное отступление
от macOS — окно статуса не привязано к иконке трея, потому что SNI не сообщает
координат, — на X11 выглядит иначе, чем на Wayland. Проверять это имеет смысл
только в настоящей VM с Ubuntu Desktop, и поведение там известно заранее:
место окна выбирает композитор, повлиять на это нечем.

**Привычную оболочку Ubuntu.** С 26.04 сеанс GNOME существует только под Wayland:
пакет `ubuntu-session` несёт единственный файл `wayland-sessions/ubuntu.desktop`,
каталога `xsessions` в нём нет. VNC работает по X11, поэтому через него виден KDE,
а не GNOME. Чтобы посмотреть именно на оболочку Ubuntu, нужен другой канал —
`gnome-remote-desktop` по RDP (с Mac подключается клиентом Microsoft Remote Desktop)
или настоящая VM с рабочим столом. На поведение охраны оболочка не влияет; влияет
она на одно — есть ли трей. В Ubuntu он есть: расширение AppIndicator включено
по умолчанию, и SNI работает так же, как в KDE.
