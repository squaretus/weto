# Ручная проверка охраны на живой машине

Netlink и таблицу маршрутов подделать нечем, поэтому часть проверок выполняется
руками на настоящем ядре. Автоматика покрывает всё остальное:

```bash
linux/scripts/dev.sh cargo test --workspace          # 510 тестов
linux/scripts/dev.sh bash scripts/tests/core-boundary-contract.sh
```

Два контракта требуют прав root — они создают интерфейсы и правила маршрутизации:

```bash
docker run --rm -t --cap-add=NET_ADMIN -v "$PWD":/repo \
    -v weto-cargo-registry:/usr/local/cargo/registry -w /repo/linux weto-rust-dev \
    bash scripts/tests/policy-routing-contract.sh

docker run --rm -t --cap-add=NET_ADMIN -v "$PWD":/repo \
    -v weto-cargo-registry:/usr/local/cargo/registry -w /repo/linux weto-rust-dev \
    bash scripts/tests/netlink-events-contract.sh
```

## Что проверено автоматикой

| Проверка | Где |
|---|---|
| Политика совпадает с macOS на 36 случаях | `weto-core/tests/policy_fixtures.rs` + Swift-двойник |
| Реестр процессов читает настоящий `/proc` | `weto-sys/tests/process_registry.rs` |
| Снимок сети читает настоящий sysfs | `weto-sys/tests/network_snapshot.rs` |
| Проба маршрута совпадает с `ip route get` | там же |
| Проба переживает policy routing `wg-quick` | `policy-routing-contract.sh` |
| Реакция на смену сети — единицы миллисекунд | `netlink-events-contract.sh` |

## Что нужно проверить руками

Настоящий туннель WireGuard — единственное, чего нет ни в контейнере, ни в тестах:
модуля ядра там нет, а dummy-интерфейс не даёт ни `DEVTYPE=wireguard`, ни настоящего
поведения при разрыве.

### 1. Туннель опознаётся как туннель

```bash
sudo ip link add dev wg0 type wireguard
sudo ip link set wg0 up
cargo run -p wetod -- --dump-network
```

Ожидание: `wg0` в списке с пометкой «туннель — да». Если пометки нет, смотреть
`/sys/class/net/wg0/uevent`: квалификация опирается на `DEVTYPE`, `tun_flags`
и `type`, и ни на что больше.

### 2. Проба видит страну

Задать токен ipinfo и выбранный интерфейс:

```bash
mkdir -p ~/.config/weto && chmod 700 ~/.config/weto
printf '%s' "<токен>" > ~/.config/weto/token && chmod 600 ~/.config/weto/token
cat > ~/.config/weto/config.toml <<'EOF'
is_enabled = true
vpn_interface = "wg0"
blocked_countries = ["RU"]
blocked_ip_ranges = []
theme = "dark"
poll_interval_seconds = 5.0
revision = 1

[[targets]]
entry = "/usr/bin/nano"
display_name = "nano"
kind = "binary"
path = "/usr/bin/nano"
EOF

cargo run -p wetod -- --check
```

Ожидание: названы обе страны и адрес. Без токена — только справочная страна
от geojs, а подтверждения нет: фаза «Выход не подтверждён», цели на паузе.

### 3. Цель встаёт вместе с туннелем, а не умирает

В одном терминале:

```bash
cargo run -p wetod -- --watch
```

В другом запустить `nano`, дождаться строки «На страже», затем:

```bash
sudo ip link set wg0 down
```

Ожидание: `nano` **не** завершается. Смена носителя трафика вердикта не отменяет
целям жизнь — она просит пробу, и решает её ответ. В выводе появляется
«Проверяю выход», а следом, когда ответ пришёл:

- страна выхода в чёрном списке или мимо белого → «Небезопасно», `nano` завершён
  (`SIGKILL`);
- сервисы не ответили → «Выход не подтверждён», `nano` остановлен (`SIGSTOP`),
  и у него есть минута: поднимите туннель обратно — `nano` продолжится сам
  (проверить `ps -o stat= -p <pid>`: `T` под паузой, `S` после), не поднимете —
  через 60 с он будет завершён с уликой «Подтверждение не получено за 60 с».

Замер: разрыв туннеля порождает событие netlink за единицы миллисекунд, дальше
идёт один обход `/proc`; секунды до реакции — это ожидание ответа гео-сервисов,
а не опроса.

### 4. Замороженных целей после выхода не остаётся

Довести `nano` до паузы по сценарию выше, затем остановить `--watch` по Ctrl-C
и проверить `~/.local/state/weto/stopped.json` и `ps -o stat= -p <pid>`.

Ожидание: файл учёта на диске есть, пока процесс стоял, а `wetod` слал ему
`SIGCONT` каждый такт. Ctrl-C штатным выходом не является (обработчика нет), так
что запись в учёте переживает выход — и следующий `--watch` обязан продолжить
процесс на старте и оставить в `~/.local/state/weto/checks.json` запись
`startupRecovery`. У приложения (`weto`) штатный выход есть, и проходит он одной
воронкой — `connect_shutdown`, а не кнопками.

Проверить её всеми четырьмя выходами: цель под паузой, и каждый раз после выхода
`ps -o stat= -p <pid>` обязан показать `S`, а не `T`, а в журнале завершений —
исход эпизода стояния («не подтверждено: сигнал продолжения отправлен…»).

1. пункт «Выход» в трее — он спрашивает «Закрыть Weto?» тем же диалогом, что
   и кнопка из пункта 2, и выходит только по «Закрыть»; Enter и Esc нажимают
   «Отмена», и тогда процесс жив, а цель по-прежнему на паузе;
2. красная кнопка «Закрыть приложение» в настройках (тот же диалог «Закрыть Weto?»);
3. закрытие последнего окна крестиком **в окружении без трея**: там приложение
   без окон завершается само, и этот путь мимо кнопок раньше оставлял цели
   стоять. Там, где трей поднялся, крестик выходом не является вовсе —
   это проверка 5;
4. `kill <pid weto>` — выход из сессии приходит тем же SIGTERM.

Удаление (красная кнопка «Удалить приложение…») — единственное место, где выход
зовут руками: цели обязаны продолжиться раньше, чем исчезнет учёт. И единственное,
где обязательство исполняет наблюдение: удаление переспрашивает ядро про оставшиеся
записи около двух секунд, а не поднявшихся называет по имени. У того диалога оба
исхода определены — «Удалить всё равно» и «Не удалять и закрыть Weto», — и ни один
не оставляет живого приложения с уже остановленной охраной. Проверять глазами:
цель, остановленную `Ctrl-Z` до паузы, weto трогать не обязан, а вот фоновое
задание, встающее обратно по `SIGTTIN`, обязано попасть в список.

### 5. Крестик прячет окно, а не снимает охрану

Проверять глазами: `linux/scripts/desktop-machine.sh ubuntu weto-ubuntu` с работающим
треем (на ванильном GNOME — расширение AppIndicator). Цель под охраной задана.

1. Открыть окно статуса и окно настроек, закрыть крестиком оба.
   Ожидание: иконка в трее на месте, процесс жив (`pgrep -x weto`), охрана
   работает — щёлкнуть «Проверить сейчас» в меню трея и увидеть новую запись
   в `~/.local/state/weto/checks.json`.
2. Щёлкнуть по иконке ещё раз. Ожидание: окно статуса открылось снова.
3. «Выход» в меню трея. Ожидание: диалог «Закрыть Weto?» — при закрытых окнах
   он открывается сам по себе. «Отмена» (и Enter) оставляет процесс и иконку
   на месте; второй «Выход», пока диалог открыт, второй копии не поднимает.
   «Закрыть» — процесса нет, цели не оставлены стоять (проверка та же, что в 4).

Отдельно — окружение без трея: запустить на ванильном GNOME без расширения,
в логе появится «трея в этом окружении нет». Ожидание: закрытие последнего окна
по-прежнему завершает приложение. Удерживать там нельзя: закрыть приложение
без окон и без иконки было бы нечем, кроме `kill`.

### 6. Ярлык доводит до программы, а не до запускателя

Глазами, в окне настроек, «Цели» → «Выбрать…». Нужны два ярлыка: любой обычный
(`/usr/share/applications/org.gnome.TextEditor.desktop` и подобные) и любой
из Steam (`~/.local/share/applications/`, строка `Exec=steam steam://rungameid/…`).

Ожидание:

- обычный ярлык добавляется молча, и в списке стоит человеческое имя из `Name=`
  — «Текстовый редактор», а не последний сегмент пути и не номер версии;
- ярлык Steam спрашивает: «Нужен файл программы», кнопки «Указать файл»
  и «Отмена». По «Указать файл» открывается второй диалог, и выбранный файл
  становится целью — под именем игры из ярлыка. «Отмена» не добавляет ничего
  и ничего не сообщает.

Проверять обязательно глазами: цель, добавленная как `/usr/bin/steam`, при падении
VPN закрыла бы Steam целиком со всеми играми, а тесты видят только то, что граница
ответила «нужен путь».

### 7. Скриптовая цель ловится по командной строке

Проверить на чём-нибудь с shebang (`npx`, любой скрипт на Node):

```bash
readlink -f "$(command -v npx)"    # путь, который надо вписать в цель
```

Ожидание: процесс завершается, хотя `/proc/<pid>/exe` указывает на интерпретатор,
а соседние процессы того же интерпретатора живут.

### 8. Содержимое настроек держит свою ширину

Под тайловым композитором (Hyprland, sway, i3) размер окна решает не приложение:
ячейка выдаётся целиком, и `default_width` в расчёт не берётся. Проверять надо
именно там, а не только под GNOME или KDE.

1. Открыть настройки и растянуть окно на весь экран. Ожидание: карточки остаются
   шириной 500 px и стоят по центру. Строки не расползаются — подпись не уезжает
   к левому краю, тумблер к правому, полосы пустоты между ними нет.
2. Сузить окно до предела. Ожидание: ниже 500×480 оно не сжимается, карточки
   и сегменты навигации не обрезаются.
3. Обе вкладки, «Настройки» и «Журнал», ведут себя одинаково.

### 9. Потолок паузы выбирается в настройках

1. Настройки → «Сеть и гео» → «Таймаут»: выбрать «5 мин». Перезапустить weto. Ожидание: выбран
   по-прежнему «5 мин».
2. Поставить цели на паузу (закрыть сервисам дорогу наружу). Ожидание: пилюля паузы
   показывает «4:5x», строка объяснения — «Ждём ответа сервисов, 4:5x до завершения…».
   Охрана при выборе потолка в «Проверку» не уходит.
3. Не дожидаясь потолка, переключить на «1 мин» на второй минуте стояния. Ожидание:
   цели завершаются ближайшим тактом, в журнале — «завершено по потолку: Подтверждение
   не получено за 1 мин».

### 10. Окна совпадают с macOS там, где тесты не видят глазами

Тексты и состав окон проверены тестами `weto-ui` и `weto-app`, но обрезку, цвет
и поведение под мышью видно только на живом столе
(`linux/scripts/desktop-machine.sh ubuntu weto-ubuntu`). Рядом держать macOS
или его снимки: отличаться окна вправе только по таблице отступлений
в `.claude/docs/modules/linux-guard.md`.

1. Пилюля цели. Добавить целью длинный путь (`~/.local/share/claude/versions/…`)
   и ярлык из меню приложений, запустить оба. Ожидание: каждая пилюля в одну
   строку, без пути под именем; длинное имя обрезано в середине «…», и окно
   статуса шире не становится; у цели-команды после имени стоит метка
   `terminal` шрифтом данных, у ярлыка метки нет, а иконка взята из его `Icon=`.
   Под паузой капсула с отсчётом янтарная, а `(i)` стоит снаружи неё, цветом
   `faint`.
2. Строка отказа прав. Целью — `nano`, запустить его от root (`sudo nano`)
   и довести охрану до паузы. Ожидание: под показаниями красная строка «Не удалось
   приостановить процессы [pid] — недостаточно прав»; когда цели снова работают,
   строка гаснет.
3. Окно обновления. Найденная версия открывает окно само: иконка 52×52,
   «Доступна новая версия Weto», галочка «Обновлять автоматически в дальнейшем»,
   кнопки «Пропустить версию», «Напомнить позже ▾» и «Обновить», промежутки между
   ними одинаковые, заметок релиза нет. Меню «Напомнить позже» раскрывается
   пунктами «через час», «через 3 часа», «через 6 часов»; выбор
   закрывает окно. Крестик тоже закрывает и откладывает на 3 часа.
4. Плитка обновления в подвале. Наведение называет состояние: «Проверить
   обновления», «X — последняя версия», «Доступна X — нажмите, чтобы открыть окно
   обновления». Нажатие гасит плитку до ответа проверки; при найденной версии
   нажатие открывает окно, а не проверяет снова.
5. «VPN-приложение» в «Сеть и гео». Не выбрано — «не выбрано» блёклым, поле
   «Команда или путь» и «Выбрать», и ряд помещается в 500 px. Выбрать клиент —
   строка меняется на имя над путём справа и корзину с подсказкой «Снять выбор»;
   корзина возвращает первое состояние.
6. Токен ipinfo. Вне фокуса в поле маска «••••••••xxxx», в фокусе — сам токен.
   Поставить курсор, ничего не менять и уйти из поля — токен в
   `~/.config/weto/token` прежний, точек в нём нет.
7. Пояснения «?». У пустого поля цели и списков в конце поля значок «?», у токена
   и «Таймаута» — после названия. Наведение пояснения не открывает, нажатие
   открывает скруглённое окно цвета карточки; набранный в поле текст значок
   прячет.
8. Линии. Пустой список целей или стран — над полем ввода линии нет, после первой
   записи появляется. Между тумблерами «Обслуживания» линий нет.
9. «Журнал». Набрать больше 20 записей (несколько пауз подряд). Ожидание: видны
   последние 20, под ними «Показаны последние 20 из N — выгрузите журнал
   целиком»; записи разделены линиями; диагностическая строка начинается с даты
   и времени «dd.MM.yyyy HH:mm:ss»; «Итог: …» — своей строкой. «Выгрузить журнал»
   видна и при пустом журнале, «Очистить журнал» — только при записях.
