# Архитектура weto

Один продукт в двух реализациях: macOS (Swift) и Linux (Rust). Кода они не делят —
только данные: токены дизайна, исходники иконки и голден-фикстуры политики.

## Стек macOS
- Swift 5.9 (tools-version 5.9), Swift Package Manager, target macOS 26.0+ (Apple Silicon).
- SwiftUI: `MenuBarExtra` со стилем `.window` плюс окно настроек в том же процессе.
  Отдельного GUI-таргета нет. VM-слой `@Observable @MainActor`, один `AppCoordinator`.
- Системные API: route-сокет `PF_ROUTE` и `connect` UDP (кто выпускает трафик),
  `getifaddrs`, `NWPathMonitor`, `SCDynamicStore` (только события сети),
  `libproc` + `KERN_PROCARGS2`, Keychain, `UserNotifications`.
- Внешних зависимостей нет. Флаги стран лежат в бандле (`shared/flags`, набор
  `HatScripts/circle-flags` под MIT).
- Распространение: PKG-установщик, автообновление через GitHub Releases `squaretus/weto`.

## Стек Linux
- Rust 2021 (floor 1.82), Cargo workspace в `linux/`, GTK4 без libadwaita.
- Системные API: `/proc`, netlink (события сети), UDP-`connect` для поиска маршрута,
  D-Bus (трей, уведомления).
- Цели: Ubuntu 24.04 LTS и новее, Arch; x86_64 и arm64. Пол GTK4 — 4.14.
  Обе архитектуры собираются нативно на раннерах GitHub, база размера бинарника
  у каждой своя.
- Установка целиком в `$HOME`: `~/.local/share/weto/<версия>` плюс симлинк `current`.
  Обновление — распаковка рядом и атомарная подмена симлинка. Root не нужен нигде.
- Сборка и тесты идут в Linux-контейнере: кросс-компиляции недостаточно, тесты обязаны
  выполняться на настоящем ядре.

## Персистентность
Доменной БД нет, правило UUID-PK неприменимо.

| | macOS | Linux |
|---|---|---|
| настройки | `UserDefaults(suiteName: "com.weto.shared")` | `~/.config/weto/config.toml` |
| журнал завершений | `~/Library/Application Support/weto/journal.json` | `~/.local/state/weto/journal.json` |
| журнал проверок | `~/Library/Application Support/weto/checks.json` | `~/.local/state/weto/checks.json` |
| токен ipinfo | Keychain, сервис `com.weto.ipinfo` | `~/.config/weto/token`, права `0600` |
| кэш обновлений | `~/Library/Caches/com.weto.app/updates/` | `~/.cache/weto/updates/` |

Журнал завершений — кольцевой буфер на 100 записей, по записи на завершённый процесс;
журнал проверок — на 50, по записи на попытку проверки подключения. Оба на обеих
платформах отдельными файлами с атомарной записью через temp + rename. Разными
файлами намеренно: вопросы разные, и одно не должно вытеснять другое.
В plist настроек журнал лежать перестал: plist читается целиком при каждом старте,
а в записи едет диагностика вплоть до сырых ответов гео-сервисов.

Токен намеренно не хранится рядом с настройками ни там, ни там: plist и TOML читает
любой процесс пользователя, и оба уходят в бэкапы.

## Сборка и запуск
```bash
cd macos && swift build                              # Debug-сборка macOS
cd macos && swift test                               # тесты
swift test --package-path macos/Packages/UpdateKit   # тесты пакета обновления
swift run --package-path macos WetoMenuBar           # запуск без бандла (без Keychain и уведомлений)
macos/scripts/make-app.sh release                    # .app → macos/.build/app/Weto.app
macos/scripts/build.sh 0.1.0                         # PKG → macos/.build/release_build/Weto-0.1.0.pkg

linux/scripts/dev.sh cargo build --workspace         # сборка Linux (в контейнере)
linux/scripts/dev.sh bash -c 'Xvfb :99 -screen 0 1280x1024x24 & sleep 2
                              DISPLAY=:99 cargo test --workspace'      # тесты
linux/scripts/dev.sh cargo fmt --all --check                   # форматирование, его требует CI
linux/scripts/dev.sh cargo clippy --workspace --all-targets -- -D warnings
linux/scripts/dev.sh bash scripts/tests/core-boundary-contract.sh      # инвариант границ ядра
linux/scripts/build.sh 0.1.0                         # tar.zst → linux/target/release_build/
linux/scripts/desktop-machine.sh ubuntu weto-ubuntu  # машина с рабочим столом для проверки глазами
```
Дисплей тестам поднимаем свой: `xvfb-run` в контейнере умеет повиснуть — стартует Xvfb
и не запускает команду вовсе.

## Раскладка репозитория
```
macos/            приложение под macOS
├── Sources/      WetoCore, WetoSystem, WetoShared, WetoDesign, WetoMenuBar, WetoHelper
├── Packages/     UpdateKit — переносимый механизм обновления, свой Package.swift
├── Tests/        по таргету на каждый модуль
└── scripts/      сборка, упаковка, shell-контракты установки и релиза
linux/            приложение под Linux (Cargo workspace)
├── crates/       weto-core, weto-sys, weto-config, weto-guard, weto-ui,
│                 weto-tray, weto-update, weto-app, wetod
├── scripts/      dev.sh (контейнер), build.sh, install.sh, desktop-machine.sh, tests/
└── docs/         ручные проверки и сценарий живого рабочего стола
shared/           то, что обязано совпадать: исходники иконки, токены дизайна,
                  голден-фикстуры политики, генератор токенов
docs/             канон дизайн-системы — общий, по платформам не делится
```
Состав файлов каждого модуля — в его документе из индекса ниже.

Голден-фикстуры — единственный механизм, которым расхождение двух реализаций
ловится машинно: один и тот же набор случаев прогоняют оба тест-раннера.
`guard-policy.json` держит политику, `journal-export.json` — формат выгрузки журнала.

## Индекс модулей
- **WetoCore** ([docs](../docs/modules/weto-core.md)) — `GuardPolicy.decide`/`decideLocal`,
  статус VPN-приложения, отпечаток снимка сети, отбор процессов с обходом дерева потомков,
  CIDR, разбор ответов гео-сервисов и GitHub Releases, отчёт о пробе (`GeoProbeReport`),
  классификация отказа (`GeoFailure`), запись журнала (`KillEvent`), её отладочные показания
  (`KillDiagnostics`) и конверт выгрузки (`JournalExport`).
- **WetoSystem** ([docs](../docs/modules/weto-system.md)) — адаптеры к macOS, каждый
  за протоколом: только на этой границе тесты и подменяют что-либо. Здесь же — проба
  маршрута (`RouteProbing`), кто выпускает трафик наружу.
- **WetoShared** ([docs](../docs/modules/weto-shared.md)) — `GuardController` (машина
  состояний, ревизии, владение пробой), `ProcessEnforcer` (кэш правил, один обход, завершение),
  `GuardVM` как фасад для UI, хранилища и обслуживание.
- **WetoDesign** ([docs](../docs/modules/weto-design.md)) — токены и компоненты
  (`docs/design-system.md`), `MenuBarImageRenderer`. Компоненты не знают о состоянии приложения.
- **WetoMenuBar** ([docs](../docs/modules/weto-menubar.md)) — UI и точка входа: попап
  со статусом, гео, живыми целями, кнопкой проверки и баннером обновления; управление —
  в окне с двумя вкладками.
- **UpdateKit** ([docs](../docs/modules/update-kit.md)) — весь механизм обновления одним
  переносимым пакетом из пяти таргетов. Ни одной константы проекта внутри: всё приходит
  `UpdateFeedConfiguration`.
- **WetoHelper** ([docs](../docs/modules/weto-helper.md)) — LaunchDaemon `com.weto.helper`
  под root: единственное место с правами. Демон сам перепроверяет релиз и ставит `.pkg`.
- **Linux-охрана** ([docs](../docs/modules/linux-guard.md)) — все крейты Linux-части:
  политика и общие фикстуры, адаптеры к sysfs, `/proc` и netlink, машина состояний,
  самообновление, отступления интерфейса от macOS. Ручные проверки —
  `linux/docs/manual-check.md`, живой рабочий стол — `linux/docs/desktop-testing.md`.

Потоки данных — [overview](../docs/overview.md). Процедуры — [runbooks](../docs/runbooks/).

## Инварианты, общие для обеих реализаций
Всё остальное — в документах модулей выше; здесь только то, без чего нельзя менять код.

- **Инвариант границ.** `WetoCore` и `weto-core` не знают о системных фреймворках:
  ни сети, ни файлов, ни UI. На Linux это проверяется машинно —
  `scripts/tests/core-boundary-contract.sh` валит сборку при появлении tokio, zbus,
  reqwest, netlink, procfs, gtk4 или rustix в графе зависимостей ядра.
- **Порядок проверок политики** (задаёт и приоритет причины, и экономию запросов): охрана
  выключена или целей нет → VPN-приложение не выбрано → не запущено → вердикт несвеж
  → ipinfo молчит → IP в чёрном списке → страна от ipinfo заблокирована → нет подтверждения
  → страна от подтверждающего заблокирована → страны расходятся → whitelist пуст → выход
  в белом списке → безопасно.
- **Белый список необязателен и спрашивается последним.** Пустой не меняет ничего; непустой
  требует, чтобы адрес попал в разрешённый CIDR **или** согласованная страна была
  в разрешённых. Чёрный список всегда решает раньше белого, поэтому одна и та же запись
  в обоих списках — не ошибка ввода. Причина отказа называет адрес, если диапазоны
  в списке есть, и страну, если список состоит из одних стран; на решение выбор причины
  не влияет.
- **Выбирается приложение, а не туннель:** вопрос «какой из `utunN` твой» пользователю
  задать нельзя. Запущенное приложение не доказывает, что трафик в туннеле, — на это отвечает
  гео, и ответ обязателен.
  [decisions/vpn-app-instead-of-tunnel](../docs/decisions/vpn-app-instead-of-tunnel.md).
- **Fail-closed строгий:** отсутствие подтверждения страны завершает цели, даже когда ipinfo
  уверенно сообщил безопасную страну. Осознанное решение владельца.
- **Fail-closed до вердикта:** потерявший свежесть вердикт (холодный старт, смена сетевого пути,
  правка настроек) даёт `verificationPending` — цели завершаются ещё до запроса к ipinfo.
  Свежесть — пара «ревизия конфигурации + отпечаток снимка сети». В отпечаток входит ровно
  то, через кого ядро выпускает вердиктный запрос: интерфейс и его локальный адрес. Состава
  интерфейсов там нет — второй VPN, живущий рядом и переподключающийся сам, вердикт
  не обесценивает.
- **Устаревший результат не возвращает safe:** у каждой пробы своя ревизия, а настройки
  и снимок читаются непосредственно перед применением.
- **Журнал объясняет каждое завершение.** Запись — один завершённый процесс (pid, родитель,
  путь, признак потомка), проход склеивается эпизодом, причина уточняется у всех записей эпизода
  разом. Эпизод, начавшийся до вердикта и закончившийся безопасным выходом, дописывает исход:
  без него запись навсегда оставалась с «подключение ещё не проверено», и завершение выглядело
  случайным. Отладочные показания — разбор свежести (что изменилось, прежний и новый отпечаток),
  интерфейс выхода, статус VPN-приложения, трассы гео-сервисов с кодом, временем и сырым телом —
  в интерфейс не попадают, только в выгрузку. Формат выгрузки общий для платформ и проверяется
  голден-фикстурой `shared/fixtures/journal-export.json`; токен в файл не попадает никогда.
- **Каждая проверка подключения тоже оставляет след.** Журнал завершений отвечает
  на «почему умерли цели» и молчит про «нажал проверить, и ничего не произошло»:
  проверка, не породившая завершения, записи не заводит. Второй журнал пишет попытки —
  повод (кнопка, смена пути, правка настроек, расписание), исход, отпечаток выхода,
  длительность и трассы сервисов, — включая те, где запрос не ушёл вовсе. Подряд
  пишется не всё: из расписания идёт только состоявшийся запрос без ответа, а пропуск
  «проба уже в полёте» — только у нажатия. Автоматические поводы просят пробу каждый
  такт, и их пропуски за пять секунд ожидания ipinfo вытеснили бы из полусотни записей
  ровно ту, ради которой журнал и ведётся. В интерфейс не попадает.
- **Свежие записи первыми** в обоих журналах и на обеих платформах. Порядок — часть
  общего формата (`order: newestFirst` в фикстуре): файл уходит на разбор, и «первая
  запись» обязана значить одно и то же. Именами ключей это не ловится, поэтому
  проверяется отдельно.
- **Проба доводится до ответа.** Пока вердикт несвеж, такт заново объявляет
  fail-closed и просит пробу; снимать летящую нельзя — такт идёт раз в секунду
  против пятисекундного таймаута ipinfo, и на медленном канале вердикт не приходил
  бы никогда. Отменяется только ожидание в окне коалесценции, а от устаревших
  показаний защищает отпечаток, снятый на старте пробы.
- **Владельца трафика спрашивают у ядра** (`connect` UDP до адреса ipinfo и `getsockname`),
  а не у конфигурации сети: `PrimaryInterface` вычисляет `configd` по сетевым сервисам,
  и у туннеля мимо NetworkExtension там остаётся подлежащий Wi-Fi. Дамп маршрута
  по умолчанию тоже не годится — клиент умеет раскладывать маршруты префиксами. Адрес пробы
  берётся у ipinfo: фиксированные публичные адреса клиенты исключают из туннеля.
- **Частота опроса системы и частота обращений к сервисам — разные числа:** опрос раз
  в секунду бесплатный (обход 820 процессов — 2 мс), гео-расписание — раз в 5 с плюс
  внеплановый запрос при смене отпечатка. Настройкой ни то, ни другое не является.
- **Отказ ipinfo не завершает цели, пока адрес доказанно тот же:** резервный сервис
  называет наш адрес, и совпадение с адресом прошлого вердикта означает ту же страну.
  Другой адрес или молчание обоих — завершение. Снисхождение выдаётся за доказательство,
  а не за давность, и смена отпечатка его отменяет.
- **UI Linux — порт, а не своя версия.** Состав и порядок экранов повторяют macOS
  поэлементно; отступления перечислены
  в [linux-guard](../docs/modules/linux-guard.md#the-ui-is-a-port-not-a-redesign)
  и продиктованы системой. Тумблера охраны нет ни на одной платформе.
- **Гео-сервисы выбраны по измерениям**: ipinfo — единственный источник IP и основной
  источник страны, подтверждение `free.freeipapi.com` с откатом на `get.geojs.io`.
  Адрес и страна от ipinfo не кэшируются никогда; подтверждение кэшируется по адресу
  (потолки 60 с и 15 мин): его квота считается на выход VPN и делится с соседями по узлу.
  Лимиты и отвергнутые сервисы —
  [decisions/geo-confirmation-services](../docs/decisions/geo-confirmation-services.md).

### Базовый образ

Отсутствует — нативные приложения без Docker в поставке. Linux-часть собирается
в контейнере из `linux/scripts/Dockerfile.dev`, но это инструмент разработки,
а не образ продукта.
